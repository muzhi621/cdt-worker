## 三、必须修复（High）

### 🔴 #1 `CRON_SECRET` 鉴权与部署指引自相矛盾 —— 启用即触发 401 让监控停摆

**位置**：`src/http/server.ts:521-531`、` .github/workflows/cron.yml`、`DEPLOY-CRON.md`

**现象**：
- `server.ts` 实现了可选 `CRON_SECRET` 校验：若配置了密钥，则 `/__cron` 必须带 `X-Cron-Secret` 头或 `?key=` 参数，否则返回 401。
- 但仓库实际触发器 `cron.yml` 调用的是 `curl https://cdt.dddde.de/__cron`，**既不带 `?key=` 也不带请求头**。
- `DEPLOY-CRON.md` 更明确告知用户公开访问：示例 URL 均为 `/__cron` 无密钥，且 FAQ Q3 写道"直接在浏览器访问 `/__cron` 即可（无需登录）"。

**后果（二选一，都是坑）**：
1. 若用户**遵循前次审计建议设置 `CRON_SECRET`**（这正是 P1#1 的初衷）→ 所有外部触发器（cron-job.org / GitHub Actions / 浏览器）全部收到 401，**监控永远不会运行**，且日志只会看到"触发地址返回 HTTP 401"，极难定位。
2. 若用户**不设置 `CRON_SECRET`** → `/__cron` 完全公开，前次审计 P1#1 想消除的"被滥用放大阿里云 API 调用 + D1 写行 + 监控停摆"DoS 面又回来了。

**当前处于最差的中间态**：一个"启用就坏、不启用就不安全"的半成品安全开关。

**修复建议（二选一，需明确决策）**：
- **方案 A（推荐，真正加固）**：让密钥贯穿部署链路。
  - `cron.yml`：`- curl -sS "https://${{ secrets.WORKER_HOST }}/__cron?key=${{ secrets.CRON_SECRET }}"`，并在仓库 Secrets 配置 `CRON_SECRET` 与 `WORKER_HOST`。
  - `DEPLOY-CRON.md`：所有示例 URL 改为 `…/__cron?key=你的密钥`，并明确"若启用 `CRON_SECRET`，所有触发源都必须带该 key"。
  - 增加约束：部署校验 `CRON_SECRET` 已设置时给出告警，避免"开了却没接线"。
- **方案 B（明确保留公开）**：若判定 `/__cron` 允许公开，则删除 `CRON_SECRET` 校验代码并在文档讲清 DoS 权衡，避免误导。

## 四、建议修改（Medium）

### 🟠 #2 `/__cron` 防抖非原子，仍存在并发竞态

**位置**：`server.ts:562-569`（`getMonitorState` 读 → 判断 → 末尾 `markMonitorRun` 写回）

**现象**：判断"是否该跑"与"标记已跑"不是原子的。两请求并发进入时，都读到旧的 `lastRun`，都通过防抖，于是**同一周期被完整执行两次**（两倍的阿里云调用、重复的 traffic_stats / heartbeat 写入、可能重复告警）。

**修复**：把"抢占"前置并用条件 UPDATE 原子化（放到周期最开始）：
```sql
UPDATE settings SET value = ? WHERE key='last_monitor_run'
  AND (value IS NULL OR CAST(value AS INTEGER) < ?)
```
`changes === 0` 即表示被别的实例抢先，直接返回 `skipped`。这样无论并发多少，一轮只跑一次。

### 🟠 #3 CSRF token 从不校验（前审计 P2#1 未落实）

**位置**：`server.ts:230-246`（`createSession`/`setAuthCookies` 生成 `cdt_csrf`），但**全代码无一处读取并比对 `X-CDT-CSRF` / `cdt_csrf` 的校验中间件**。

**风险**：仅靠 `SameSite=Strict` 兜底。在 `*.workers.dev` 子域并存的场景下，`SameSite` 是"站点级"而非"源级"，恶意 sibling `workers.dev` 应用可发起同站跨源 POST 触发副作用（改配置、删账号等）。

**修复**：
- 在写操作（`PUT/POST/DELETE` 且需 admin 的路由）前加中间件，比对 `X-CDT-CSRF` 请求头与 `cdt_csrf` Cookie 是否相等；或
- 在 README/部署文档**强制**"关闭 `workers.dev` 路由，仅用自建域"（目前文档未强调）。

### 🟠 #4 阿里云签名 `percentEncode` 处理 `%2B`/`%20` 存在隐患（前审计已知回归风险，仍需实测）

**位置**：`src/provider/aliyun.ts:37-42`

```ts
.replace(/%2B/gi, '%20');   // ← 这一行有问题
```
`encodeURIComponent('+')` 得到 `%2B`，阿里云服务端会解码为 `+` 后重签为 `%2B`；但客户端把它错签成 `%20`，**一旦签名参数值含字面量 `+`，将偶发 `SignatureDoesNotMatch`**。当前固定参数（AccessKeyId/Timestamp/Nonce 等）不触发，但 `extras`（如备注类、异常 RegionId/InstanceId）在特定取值下可能触发。

**修复**：与阿里云官方 `percentEncode` 对齐——保留 `%2B`，仅做 `space→%20`、`*→%2A`、`~ 保留`：
```ts
function percentEncode(v: string): string {
  return encodeURIComponent(v)
    .replace(/%7E/gi, '~')
    .replace(/%2A/gi, '*');
}
```
并做一次真实 API 回归（流量/状态/启停/账单），把签名逻辑纳入单测。

### 🟠 #5 SMTP（`cloudflare:sockets`）缺乏真实环境验证

**位置**：`src/notify/smtp.ts`

SMTP 路径依赖 `cloudflare:sockets`（在 `nodejs_compat` 下可用），但仓库内**无任何测试或验证脚本**。465 隐式 TLS + AUTH LOGIN 与主流邮箱（QQ / 163 / Gmail）的互通性、以及 `SmtpConn.reply()` 多行回复解析在异常网络下的健壮性，均未经验证。建议 `wrangler dev` 或部署后做一封测试邮件冒烟；并确认 SMTP 出站 TCP 不计入子请求上限、但每次通知建连成本较高，应与主动通知错峰。

### 🟡 #6 `init-status` 无鉴权，泄露 `envPasswordSet`

**位置**：`server.ts:91-95`、`routes` 中该接口无 `scope`

返回 `initialized` 与 `envPasswordSet` 布尔。后者会暴露"是否配置了恢复密码 Secret"，属低危信息泄露。建议加 admin 鉴权，或至少移除 `envPasswordSet` 返回（前端其实在登录页才需要该提示）。

## 六、架构与设计评价

**做得好的地方（应予保持）**：
- **模块边界清晰**：`index → http → engine → provider/store/notify/security` 分层合理，纯函数策略与 I/O 解耦，利于单测。
- **幂等设计扎实**：阈值/定时/保活均用 `action_events` 去重键，且定时开关机的"跨午夜窗口归属"处理正确（避免同一次逻辑关机被拆成两天重复执行）。
- **时区处理正确（本项目最易错点，做对了）**：`toZone` / `zoneFields` / `localCycle` 全程用配置时区墙钟，规避了 UTC 月份错位导致的账单账期错位与定时漂移。
- **加密正确**：AES-GCM + Web Crypto，12 字节随机 IV，密钥来自 Secrets，符合原项目安全模型。
- **错误兜底到位**：`handleRequest` 统一把 handler 异常转成可读 JSON 500，避免 Cloudflare 默认纯文本 500 导致前端只显示"操作失败"。
- **RAM 最小权限文档完善**：README 给出系统策略与自定义策略两套，安全指引质量高。

**值得商榷的设计取舍**：
- **外部 HTTP 触发 vs 原生 Cron**：为避开"5 个 Cron 免费额度"改用外部 `/__cron`，引入了"公开 URL + 密钥"的运维复杂度（也正是 #1 矛盾的根源）。实际上只需 **1 个**原生 Cron Trigger（≪5），更简单也更安全，`scheduled()` 入口已就绪。建议在额度允许时回退原生 Cron，`/__cron` 降级为受保护的手动入口。
- **无自动化测试**：重试/退避、`percentEncode`、时区窗口、幂等键、账单缓存 TTL 都是高 bug 密度逻辑，却零覆盖。
