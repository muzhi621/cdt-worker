## 一、总体结论

代码分层清晰（http / engine / provider / store / security / notify），幂等与并发抢占、时区/账期处理、AES-GCM 加密整体是对的，**可维护性处于良好水平**。本次发现的核心问题集中在三类：

1. **前一轮整改有 2 项实际未落地**（`init-status` 信息泄露、CSRF 只发不验）——属于「说了做了但代码里没有」，本次按 Blocker/Warning 重新提出；
2. **免费额度的真实瓶颈不是 D1/请求数，而是「每请求 10ms CPU」**——`Intl.DateTimeFormat` 与 PBKDF2 是最大嫌疑；
3. **新加的触发源功能存在重复 D1 读写与force 跑监控的放大面**（自测功能可被打爆）。

**先给结论性的额度判断（5 账号 / 5 分钟间隔 / 288 周期每天）：**

| 维度 | 免费额度 | 估算用量 | 占比 | 结论 |
| --- | --- | --- | --- | --- |
| Workers 请求 | 100,000 /天 | 定时 288 × 渠道数（≤3）+ 前端若干 ≈ 1.5k | ≈1.5% | **安全** |
| D1 行读取 | 5,000,000 /天 | ≈35 行/周期 ≈ 10k/天 | ≈0.2% | **安全** |
| D1 行写入 | 100,000 /天 | ≈22 行/周期 ≈ 6.3k/天 | ≈6% | **安全** |
| Cron 触发器 | 5 /账号 | 当前应为 0（原生 Cron 已关闭） | — | **需人工确认无残留** |
| **CPU / 请求** | **10 ms** | 单周期含约 20–30 次 `Intl.DateTimeFormat` 构造 + 10 次 AES 解密 + 15 次 HMAC 签名 | **偏高** | **⚠ 主要风险** |
| 登录 CPU | 10 ms | PBKDF2 60,000 次迭代 | **可能超限** | **⚠ 需实测** |

> 结论：D1 与请求数远未触顶，**省钱重点应放在「降低单请求 CPU」和「减少无谓写操作」**，而不是压缩监控频率。

## 二、Blocker（阻断项）

### B1 · `init-status` 仍在泄露 `envPasswordSet`，且与此前整改结论矛盾

- 位置：`src/http/server.ts` 路由表 `/api/v1/system/init-status`（约 L590）
- 现状：

```ts
{ method: 'GET', pattern: '/api/v1/system/init-status', handler: async (ctx) => json({
    initialized: await store.isInitialized(ctx.env),
    // 已通过 Cloudflare 环境变量配置恢复密码（未初始化时也可直接用它登录）
    envPasswordSet: envPassword(ctx.env) !== '',   // ← 未鉴权接口，泄露后门是否存在
  }) },
```

- 而 `login()` 里的注释写着「不再通过 init-status 暴露」——**代码与注释/整改记录不一致**，说明该处改动在并行编辑中丢失。
- 风险：任意未登录访客可探测 `ADMIN_PASSWORD` 后门是否启用，为定向爆破提供情报。
- 修复（1 行）：

```diff
-      envPasswordSet: envPassword(ctx.env) !== '',
```

- 前端已不依赖该字段（改为读登录失败响应的 `env_password_available`），删除无副作用。

## 三、Warning（必须修复）

### W1 · CSRF「只发不验」：后端从未校验 `X-CDT-CSRF`

- 位置：`src/http/server.ts` 仅 `setAuthCookies()` 下发 `cdt_csrf` cookie（L266–271），全文件**没有任何读取/比对 `X-CDT-CSRF` 的逻辑**；前端每次写请求都带该头。
- 风险：双提交防护形同虚设（当前仅靠 `SameSite=Strict` 兜底，可缓解跨站但无法防御同站子域/未来改动）。
- 修复：在鉴权通过后、进入 handler 前加校验（会话鉴权 + 非安全方法）：

```ts
// 会话鉴权 + 非安全方法 → 校验双提交 token
if (principal?.admin && !['GET','HEAD','OPTIONS'].includes(request.method)) {
  const header = request.headers.get('X-CDT-CSRF') || '';
  const cookie = /(?:^|;\s*)cdt_csrf=([^;]+)/.exec(request.headers.get('Cookie') || '')?.[1] || '';
  if (!header || !cookie || !(await constantTimeEqual(header, cookie))) {
    return error('csrf_failed', 'CSRF 校验失败，请刷新页面重试', 403);
  }
}
```

### W2 · 登录限流实际只有内存档，`login_attempts` 只 INSERT 不 COUNT

- 位置：`login()`（L151）只有 `allowRate('login:'+ip, 8, 15min)`；失败时 `INSERT INTO login_attempts`（L172）却**从未被查询**。
- 风险：Cloudflare 是多 isolate 分布执行，内存计数跨实例失效，攻击者可分布式爆破；表里还会无限增长。
- 修复：失败时先 COUNT 近 15 分钟失败次数，超限直接 429；成功登录时清理该 IP 记录。

### W3 · 「测试渠道」可无限次 force 跑整轮监控（放大面）

- 位置：`testTrigger()` → `runMonitorCycle(env, true)`（绕过防抖）+ 内部 `flushOutbox()` 会真实发通知。
- 风险：连点 = 反复调用阿里云 API（限流/封禁风险）+ 通知轰炸 + 逼近 CPU 上限。
- 修复：对 `test` 接口加限流（如每渠道 60 秒一次，用 `action_events` 记录），并在响应中说明；可选 `skipNotify` 参数。

### W4 · PBKDF2 60k 迭代 + Free 10ms CPU，登录有超限风险

- 位置：`src/security/security.ts` `PBKDF2_ITERATIONS = 60000`
- 风险：登录是单请求内最重的 CPU 开销，免费计划 CPU 上限 10ms/请求，超限会直接返回错误（未实测复现，但属高风险项）。
- 修复建议：实测（Dashboard → Worker → 登录请求 CPU 时间）；若接近上限，降到 20k–30k 并保留算法升级路径（哈希串已带 `i=` 版本号，可平滑迁移）。

### W5 · `Intl.DateTimeFormat` 每账号每周期重复构造 20–30 次（CPU 浪费）

- 位置：`src/engine/time.ts` `toZone()` / `zoneFields()` 每次调用都 `new Intl.DateTimeFormat(...)`；`processAccount` 每账号每周期调用 `toZone` + `zoneFields` + `localCycle`×2 + `executeScheduledAction` 内 `zoneFields`。
- 风险：Intl 格式化器构造是出了名的昂贵（毫秒级），5 账号 × 多轮调用足以吃掉可观 CPU。
- 修复：模块级缓存（按 `timezone` 复用实例）：

```ts
const fmtCache = new Map<string, Intl.DateTimeFormat>();
function formatter(timezone: string): Intl.DateTimeFormat {
  let f = fmtCache.get(timezone);
  if (!f) { f = new Intl.DateTimeFormat('en-US', { timeZone: timezone, hour12: false, /* …字段… */ }); fmtCache.set(timezone, f); }
  return f;
}
```

### W6 · 每次触发多做了 2 次无谓 D1 读（且存在读-改-写竞态）

- 位置：`/__cron` 先 `getTriggerState()`（1 读）→ `touchTriggerSource()` 内部**再** `getTriggerState()`（1 读）+ 写（1 写）；`runMonitorCycle` 内 `checkTriggerGaps` 又读一次。
- 风险：单次触发 3–4 次 D1 操作；`touchTriggerSource` 的读-改-写在多渠道并发时还会互相覆盖 `trigger_seen`。
- 修复：把已读到的 `seen` 传进 `touchTriggerSource(env, source, nowSec, seen)`，一次读一次写；`checkTriggerGaps` 复用同一次读取结果。

### W7 · `deleteActionEvent(thresholdKey)` 每账号每周期无条件执行

- 位置：`src/engine/engine.ts:196`（`if (!overThreshold) await store.deleteActionEvent(...)`）
- 风险：正常情况下 99% 的周期该键并不存在，白白产生 N 次 DELETE（D1 行数计费 + CPU）。
- 修复：仅在本次周期此前确实记录过阈值事件时才删（内存/局部标记，或先 SELECT 存在性）。

### W8 · `ADMIN_PASSWORD` 后门常驻

- 位置：`login()` 兜底分支；已有登录成功日志提示删除，但变量本身无过期机制。
- 修复建议：用后即删（文档已提示）；可增加「用 env 密码登录只签发短会话（如 30 分钟）」降低窗口期。

### W9 · Webhook / proxyUrl 为任意用户可控 URL（出网面）

- 位置：通知配置 webhook.url、telegram proxyUrl，由 Worker 直接 `fetch`。
- 风险：Worker 会被用作出网代理，向外发送凭据模板内容（数据外发）；虽非典型 SSRF（CF 无内网元数据），但属于供应链/外发面。
- 修复建议：限制协议为 https、拒绝内网/回环地址解析（若支持）、并在 UI 提示风险；敏感度取决于你对配置者的信任模型（**待澄清**）。
