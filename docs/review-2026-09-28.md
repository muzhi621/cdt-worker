## 二、🔴 P0（必须合入前修复，不接受下版本补）

### P0-1（即三轮 T1）`peekBillingText` 未用 `billingSnapshot`，通知轮次每账号多付 1 subrequest

**位置**：`src/engine/engine.ts:197-208`

```ts
async function peekBillingText(): Promise<{ balance: string; cost: string }> {
  ...
  const bal  = await store.billingCache(env, account.id, 'balance', '', 6);          // 第 1 次 D1 读
  const bill = await store.billingCache(env, account.id, 'instance_bill', localCycle(now, config.timezone), 6); // 第 2 次 D1 读
  ...
}
```

同一文件 `engine.ts:346-348` 的**刷新处**早已用合并版 `billingSnapshot`，但**通知路径（阈值/保活/状态变化，即真正发通知的轮次）仍是两次独立读**。性质与三轮 T1 完全一致，且三轮已明确「按语义枚举全部调用点」——此处正是漏掉的那一个。

**影响**：每次发通知的轮次，每账号确定性多 1 次 subrequest（2→1 的缺口）。5 账号同轮发通知 = 每轮 +5，把「账单未命中 + 发通知」档从 35 拉回 40，距 50 上限余量只剩 10。确定性浪费，与缓存命中无关。

**改法**（三轮已给，≈10 行）：
```ts
const snap = await store.billingSnapshot<{amount?:number;currency?:string;totalCost?:number}>(
  env, account.id, { balance: '', instance_bill: localCycle(now, config.timezone) }, 6);
if (snap.balance?.hit && snap.balance.value) billingText.balance = `${snap.balance.value.amount} ${snap.balance.value.currency||''}`.trim();
if (snap.instance_bill?.hit && snap.instance_bill.value) billingText.cost = `${snap.instance_bill.value.totalCost}`;
```

### P0-2（即三轮 T2）`summary()` 同样是两次独立查询

**位置**：`src/engine/engine.ts:544-549`

`/api/v1/status` 数据源 `summary()` 里账单读取仍拆两条 `billingCache`（balance / instance_bill）。该接口前端状态页每次刷新都调用，是用户高频行为；且这里 TTL 传 `8760`（取缓存即可），所以每次都实付 2 次读。5 账号 × 每次刷新 = 多 5 subrequest。与 P0-1 同因同源，改法完全一致（切 `billingSnapshot`，TTL 传大值即可）。

> **【批判性分析】** 为什么这两处值得单独成 P0、且必须现在修：三轮把 R2 列为「R1 单独修只到 48 仍贴线，必须叠加 R2 才有安全余量」。现状是 R1 修了、R2 修了一半。刷新路径的安全余量是真的，通知/状态页路径的不是。而通知与状态页恰恰是监控存在的理由。挂着不修 = 把「唯一会重新逼近上限」的确定性成本长期暴露在线上。
>
> **【决策锁校验】** 修复判定锁：① 改完必须用 `grep billingCache` 全仓确认仅剩 `billingSnapshot` 内部一处实现，无残留独立调用（按语义而非按位置修复）；② 补回归测试「`summary()`/`peekBillingText` 单次调用只产生 1 次 billing 查询」（三轮已建议，至今缺失）；③ 重新核算预算表，确认「账单未命中 + 发通知」回到 35。

## 三、🟠 P1（本迭代内修复或显式拆 ticket + TODO）

### P1-1 `ddnsTestCredential` 缺限流（违反标准「测试类按钮必须限流」）

**位置**：`src/http/server.ts:1483`（handler）/ 路由 `:177`

`ddnsTestCredential` 触发一次出站 `provider.query`（打 DNS 厂商 API）。标准维度 B 明确要求「任何会调用外部 API 或产生副作用的接口都要限流（含'测试'类按钮）」。同文件的 `notify/test`（:664 `allowRate('notify-test:...')`）、`control`（:567）都加了 `allowRate`，唯独这个新增的测试接口没有。

**影响**：持有 admin 的会话（或被 CSRF 利用，尽管已防）可连点「连通测试」反复打厂商 API，触发厂商侧限流/计费，且无服务端闸门。

**改法**（与其他测试接口对齐，≤5 行）：
```ts
if (!allowRate('ddns-test:' + clientIP(ctx.request), 5, 60_000)) {
  return error('rate_limited', '连通测试过于频繁，请稍后再试', 429);
}
```
`ddnsSyncHandler`（force 同步，:1514）同样无 `allowRate`，但同步幂等、且需 admin，风险更低，建议一并加 `allowRate('ddns-sync:...', 3, 60_000)` 防误点刷爆厂商。

## 四、🟡 P2（记 ticket，排期修）

### P2-1 分组参数格式未校验（静默回落到 1970/00:00）

**位置**：`src/http/server.ts:1290` `parseGroupBody`

`anchorAt` / `anchorDate` / `switchTime` 仅 `String().trim()`，无格式校验。用户若填错（如 `2026/1/1`、`25:00`、`abc`），`splitAnchorAt`/`parseHm` 返回空 → 分组静默以 `1970-01-01 00:00` 或 `03:00` 为原点运行，无任何报错。属于「前端做了校验就当后端安全」的反模式（标准维度 B）。

**改法**：后端白名单校验——`switchTime` 必须匹配 `^([01]\d|2[0-3]):[0-5]\d$`；`anchorDate` 匹配 `^\d{4}-\d{2}-\d{2}$`；`anchorAt` 匹配 `^\d{4}-\d{2}-\d{2}([ T][0-2]\d:[0-5]\d)?$`；不符返回 400。

### P2-2 `ddnsSaveMembers` 时段字段未校验

**位置**：`src/http/server.ts:1342` `windowStart`/`windowEnd` 仅 `trim`，无 `HH:MM` 校验。

**影响**：window 模式填非法时段 → `parseHm` 返回 `null` → 该机器被静默跳过（不命中），用户看不到任何报错，排班「看起来配了却不生效」。

**改法**：若 `windowStart`/`windowEnd` 非空则用 `parseHm` 校验，非法返回 400；或在保存时把非法值当「未配置」并明确提示。

### P2-3 `ddnsCreateRecord` 不校验 `credentialId` 存在性

**位置**：`src/http/server.ts:1369` `credentialId: Math.max(0, Math.floor(Number(b.credentialId) || 0))`

允许传任意 `credentialId`（含不存在的 id 或 0）。`0` 或悬空 id → 记录无可用凭据 → 同步时 `readCredential` 回 `{}` → 厂商鉴权失败。前端只提供合法凭据，故实际风险低，但后端应拒绝「`>0` 且 `ddns_credentials` 无此行」的引用（与删除时的 `countRecordsUsingCredential` 对称）。

### P2-4 DDNS 同步与监控共用同一调用 subrequest 预算（需加护栏/可观测）

**位置**：`src/http/server.ts:1209-1218` `runDdnsSync` 在监控周期尾部同一 Worker 调用内执行。

稳态下 `rec.current_ip === targetIp` 前置跳过（sync.ts:108），DDNS 每轮 **0** fetch、0 D1 读，符合「幂等省额度」。但**切换时刻**：若 N 个记录同时需变更，每个 = `query`+`update` = 2 fetch，叠加在监控的 ~35 之上。多分组多记录时可能逼近 50，触发 1101 会**中断整轮 cron（含监控主流程）**——尽管下一轮自愈，但那 5 分钟窗口的监控/通知可能漏掉。

**判定**：因幂等 + 切换事件低频，**不列 P0**，但属标准维度 C「新增每轮操作前先算一年成本」的待办。建议：① 在 `runDdnsSync` 内加「本轮 DDNS 已用 subrequest 计数上限」（如超 20 即停止本轮回填、下轮续做）；或 ② 至少在 `docs/code-review-standards.md` 预算表新增「DDNS 同步（切换时刻突发）」档位并标注观察 `Exceeded Subrequests` 指标。

### P2-5 遗留凭据迁移失败被静默吞掉

**位置**：`src/store/schema.ts:245-247`

```ts
try { await migrateInlineCredentials(env); } catch { /* 迁移失败不影响启动，下次请求重试 */ }
```
但 `schemaReady` 在随后即置 true，本 isolate 内不会再重试；且 catch 无任何日志。若迁移因某条脏数据持续抛错，问题不可见。

**改法**：catch 内 `await addLog(env, 'error', 'DDNS 遗留凭据迁移失败：' + e.message).catch(()=>{})`，便于从日志页发现卡住的迁移。

### P2-6 （后续）补「1 次 billing 查询」回归测试

三轮已建议、至今未落。待 P0-1/P0-2 修复后，在 `test/*` 增加断言 `summary()` 与通知路径单次调用只产生 1 次 billing 查询，锁住语义防回归。

## 五、做得好的地方（本轮新看到的，按标准阶段 3 要求先肯定）

- **凭据独立实体 + 幂等迁移**（DDNS `store.ts` / `schema.ts`）：`ddns_credentials` 表 + `credential_id` 引用，一份凭据被多条记录复用；迁移 `WHERE credential_id=0 AND credential_enc<>''` **只搬密文、不重加密、只跑一次**，既幂等又零风险。这是比「每条记录各存一份」更正确的设计。
- **`readCredential` 单一真源**（store.ts:331）：优先 `credential_id` 引用、缺失回退历史 `credential_enc`，调用方无需关心凭据存在哪。符合标准维度 D「同一语义收敛到单一函数」。
- **凭据安全面**：AES-GCM 加密；明文/密文均不出后端（overview 只回脱敏值，`ddnsOverview` 显式 `credential_enc: ''`）；`requestJson`（types.ts:77）错误只回 `url.split('?')[0]`，**AK/SK 永不进错误文案**；`sk` 仅用于 HMAC 不传输；删除被引用凭据返回 409。整套无密钥泄露面。
- **鉴权/CSRF 复用既有机制**：DDNS 全部路由 `scope:'admin'`（server.ts:165-182），cookie 会话走 `cdt_csrf` 双提交校验（:879），API Key 走 header 天然免疫——新增接口**没有引入任何鉴权/CSRF 缺口**。
- **排班算法纯函数化 + 时区正确**：`scheduler.ts` 全用 `Intl` 取 IANA 墙钟（非 UTC 硬减偏移），跨午夜窗口 `start>end` 正确命中；`interval` 复用 `rotate` 内核、以 anchor 时刻作切换点——逻辑清晰、可测。
- **DB 批处理**：`saveMembers`/`deleteGroup`/`deleteMachine`/`deleteCredential` 均用 `DB.batch`（1 subrequest），符合维度 C。
- **前端转义统一**：DDNS 所有动态插入走 `escDdns`（转义 `&<>"`），无裸 `innerHTML` 拼用户串；`openModal({html})` 的所有调用方均用 escDdns 构造。
- **测试新增前端通测**：`test/web-forms.test.ts`（21 例）用「代码标记切片 + vm 执行真实内联源码」覆盖日期控件与排班弹窗，是本项目前端自动化测试从 0 到 1 的突破。
