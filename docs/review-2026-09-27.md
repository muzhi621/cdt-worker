## 结论速览

整体质量**高于**同类个人项目平均水平：并发去重、幂等键、时区墙钟、错过窗口补偿、密钥托管这几处
设计得相当扎实，注释也在解释"为什么"而不是复述"做了什么"。72 个测试覆盖了全部纯函数边界。

但有 **2 个 P0 会在免费额度上硬性翻车**，以及若干一处能触达真实云资源破坏的校验缺口。

## 一、先说做得好的地方（不该被后面篇幅淹没）

- **`tryAcquireMonitorSlot` 的条件 UPSERT 原子抢占**（`store.ts:93`）。用一条语句完成"检查+占位"，
  并发触发只有一轮能抢到，比旧的"读→判→写"三步法彻底正确。这是本项目最重要的一个范式。
- **`shouldNativeRun` 做成纯函数并明确"跳过的轮次绝不写 `trigger_seen`」**（`triggers.ts:83`）。
  这行注释抓住了一个极隐蔽的自我掩盖缺陷：时间戳被自己刷新，断档告警就永远不会响。
- **开机补偿与关机补偿共用 `windowOver`**（`engine.ts` + `time.ts:109`）。之前开机方向漏了补偿，
  导致跨午夜窗口的实例整天不启动。抽成通用函数后两边语义天然对称。
- **默认值单一数据源**：`DEFAULT_CONFIG` 派生 `DEFAULT_SETTINGS`，避免两处漂移的历史 bug。
- **`formatWallClock` / `zoneFields` 复用 `Intl.DateTimeFormat` 实例缓存**（`time.ts:9`）。
  直接针对 Free 计划 10 ms CPU 上限做的优化，方向完全正确。
- **登录成功后轮换而非复用 token**（`server.ts:322`）， session fixation 防护到位。
- **`resolveCronSecret` 解密失败时回退 env 而非抛错**（`store.ts:115`）—— 刻意让密钥系统故障
  不至于放大成监控中断，这个取舍想得很清楚。

## 二、🔴 P0-1 单轮监控的子请求数越过 Free 计划 50 上限

**严重度：🔴 P0（不修就不要跑 5 个账号）**

### 现象
Free 计划 **subrequests = 50 / 请求**[^1]，超出直接返回 1101 `Worker exceeded resource limits`，
整轮监控静默失败。一次 `scheduled()` 调用的子请求构成：

| 来源 | 数量 | 位置 |
|---|---|---|
| `getTriggerState` + `getMonitorState` + `touchTriggerSource` | 3 | `index.ts:28,37,40` |
| `getMonitorState`（`runMonitorCycle` 内重复读） + `getConfig` + 槽位抢占 | 3 | `server.ts:1057,1074,1077` |
| **每账号**：阿里云 2 个 fetch + `updateRuntime` + `addTrafficStat` | 4 × N | `engine.ts:162-183` |
| **每账号**：账单 2 次缓存读（+ 未命中时的 2 fetch + 2 次 `setBillingCache`） | 4~6 × N | `engine.ts:311-343` |
| `flushOutbox`（`listPendingOutbox` + 每行的 `markOutbox*`/`addLog`） | 1~11 | `engine.ts:541` |
| 日志清理日任务（`recordActionEvent` + 5 个 DELETE） | 6 | `server.ts:1101-1107` |
| 周期汇总 `addLog` | 1 | `server.ts:1118` |
| 冷 isolate 时 `ensureSchema` 的 DDL batch | 1 | `index.ts:12` |

### 实测估算

```
固定开销                     4
5 账号 × 10~12（账单缓存命中/未命中）  50~60
flushOutbox + cleanup + 日志   8
─────────────────────────────
合计                        ≈ 62~72   ← Free 上限是 50
```

**结论：超 12 个以上。** 而且这是"账单缓存全部命中"的乐观情况。真实场景里只要
① 任意账号查询报错（每错一次 `addLog` +1）；② 通知队列有积压（`flushOutbox` 每行 +1~3）；
③ 10 分钟账单 TTL 到期（连续 5 个账号同时 miss，+10），立刻爆掉。

更糟的是：**账号数每增加 1 个就 +10~12**，所以现在这个代码在 5 账号下已经在悬崖边，
加到 6~7 个必然翻车。

### 建议改法（按性价比排序，预计可压到 ~28）

1. **把连续的 D1 写合并成 `DB.batch()`**，`batch` 只算 **1 个** subrequest。
   当前 `updateRuntime` + `addTrafficStat` 是两次独立 `run()`（`engine.ts:180,182`）→ 合成一个 batch，
   每账号省 1；`addLog` 逐个写的地方同理。**预计省 6~10 个。**
2. **账单查询降频**：`BILL_TTL_HOURS = 10/60`（10 分钟）在每 5 分钟一轮的节拍下，
   平均每 2 轮才真查一次，而 5 个账号会**同时** miss 造成尖峰。改为
   - 账单加**抖动 TTL**（每个账号 `10min + accountId % 7 min`），把尖峰打散；
   - 或把整个账单刷新包在一个 `DB.batch()` 里。
   **预计省 8~20 个（账单 miss 轮）。**
3. **断档检查挪到槽位抢占之后**（见 🟡 P2-1，现位置白跑），**省 7 个且只在需要时付**。
4. **去掉 `runMonitorCycle` 里重复的 `getMonitorState`**（`server.ts:1057` 与 `index.ts:37` 读了同一个东西），
   由调用方透传。**省 1 个。**
5. **清理日任务挪进 `batch()`**，`recordActionEvent` + 5 个 DELETE 合成 1~2 个。**省 5 个。**
6. **把 `CONCURRENCY` 上限从 5 降到 3**：Free 计划同时出站连接上限是 **6**，
   现在每账号并发 2 个 fetch × 5 = 10，已经超了。降 3 可显著改善 1101/超时风险。

> 改完后建议加一条回归测试/文档：*「单轮监控 subrequest 预算 ≤ 40」*，并把这条写进审查标准。
> 这比事后对着 1101 抓瞎要可靠得多。

## 三、🔴 P0-2 密钥经 URL 参数传入，会被 Cloudflare 日志留存

**严重度：🔴 P0（可直接被日志读到）**

### 问题
`server.ts:736` 与 `:961` 接受 `?key=`；`server.ts:847` 还额外接受 `?secret=` 做下载鉴权。
URL 查询串会进入：

- `wrangler tail` / Dashboard → Workers → Logs（项目已开 `[observability] enabled = true`）
- CF Logpush / Observability 的 `ClientRequestURI`
- 浏览器历史、Referer（同域跳转一般不发，但外链会）
- 自建驱动脚本里的 `DEFAULTS.url`（`selfhost.ts:18`）—— URL 里若带 `?key=`，密钥就被写进
  `/opt/cdt-trigger/driver.mjs` 并可能进入备份

现在能跑通全靠 header 通道，但**复制粘贴的教程链接极容易把 `?key=xxx` 留在 URL 里**。
一旦泄露，攻击者只要把 `native`/`selfhost` 等渠道开关打开就能驱动监控（虽然不能直接控制实例，
但能消耗阿里云 API 额度与 D1 写入）。

### 建议改法
1. **鉴权只认 `X-Cron-Secret` 请求头**，`?key=` **保留但降级为"兼容通道"**：
   仅当请求同时带 `X-Cron-Forwarded` 头（由本 Worker 自己生成、第三方不会携带）时才接受，
   或者干脆记录一条 warning 日志提示"密钥出现在 URL 中"。
2. **下载链接去掉 `?secret=`**：`secret` 只用于拼脚本内容，不该参与鉴权。
   现在把鉴权和内容注入混在一个参数上是设计耦合，拆开后 `?secret=` 甚至可以完全删除。
3. **教程区块的示例 URL 一律不带参数**，或在旁边加一行红字警示。
4. 在 `getCronSecretHandler` 里加一个开关：`reveal=1` 时才给出可复制的完整触发命令。

> 这一条不修，其余安全加固都是在给"钥匙插在门上"的房间换锁。

## 四、🟠 P1 清单

### P1-1 设置写入无范围校验 —— 一个字段能触发批量停机

**位置**：`store.ts:228-238`（`getConfig` 的 `parseInt(...) || DEFAULT`）、`server.ts:416-435`（`saveConfig`）

`parseInt(x) || default` 有个致命陷阱：**`0` 会回退到默认值，但负数会忠实采用**。实测：

```
raw="-1"    → threshold=-1,  apiInterval=-1,  monitorInterval=-1
raw="-50"   → threshold=-50
raw="1e9"   → 全部变成 1      （parseInt('1e9') === 1，只解析到 '1'）
```

链路后果：
- `trafficThreshold = -50` → `overThreshold = percentage >= -50` **恒真**
  （`engine.ts:188`）→ 一旦 `due`，就记录阈值事件 → `thresholdAction === 'stop_and_notify'`
  → **`aliyun.controlInstance(..., 'stop')`**。**所有在线实例被停掉**，同时 Outbox 灌满告警。
- `apiInterval = -1` → `engine.ts:154` 的 `interval` 为负 → `due` 判定恒真 →
  每轮都打阿里云 API，直接触发 `Throttling.User`，还会污染其它账号（注释里已经写过这个坑）。
- `monitorInterval = 0/-1` → `shouldNativeRun` 恒返回 true + 防抖 `debounceSeconds = 0`
  → 每轮跑完整监控。

前端对 `trafficThreshold`（1–100）、`monitorInterval`（1–1440）、`logRetentionDays`（1–3650）
有校验，唯独 **`apiInterval` 没有**（`index.html:2804` 直接 `parseInt(... ) || 60`），
而且前端校验只是 UI 层，API 客户端 / curl / 未来新增的 API Key 全都绕得过。

**建议**：在 `saveConfig` 里加统一的数值白名单校验（后端硬校验），
并把 `apiInterval` 的合理下界设为 60 秒。顺带把 `parseInt(...) || DEFAULT` 换成
`Number.isFinite(n) && inRange(n) ? n : DEFAULT`。

### P1-2 通知凭据在 D1 里是明文，与 AK/SK 的加密强度不一致

**位置**：`store.ts:10-33` / `server.ts:449`

账号 AK/SK 用 AES-GCM 加密存 `access_key_*_enc`，但 `notifications`（telegram token、
smtp password、webhook secret、serverchan key、pushplus token）是 `JSON.stringify` 直接
写进 `settings.value` 的明文。

同一张 `settings` 表、同一类敏感数据、两套强度。而且 `GET /api/v1/config` 会把它们返回给前端
（只脱敏成 `xxxConfigured`，本身没错），一旦 D1 只读权限/备份/Time Travel 恢复出现意外，
凭据是裸奔的。

**建议**：复用 `security.encrypt/decrypt`，存成 `enc:v1:...`。改动很小
（`saveConfig` 写之前加密、`getConfig` 读之后解密），但能统一安全口径。
至少要在 `DEFAULT_CONFIG` 的注释里写明"当前为明文，待加密"——否则以后没人知道这是有意还是遗漏。

### P1-3 限流缺口：三个会打外部 API 的接口没有限流

| 接口 | 位置 | 风险 |
|---|---|---|
| `POST /api/v1/notify/test` | `server.ts:588` | **真的外发通知**。连点会打爆 Telegram/SMTP/推送服务，且触发频率限制后静默失败 |
| `POST /api/v1/accounts/:id/actions/:action` | `server.ts:493` | 直接调 `StartInstance`/`StopInstance`，无冷却 |
| `DELETE /api/v1/accounts/:id` | `server.ts:650` | 无冷却（破坏性，虽然需要确认） |

对比：`refresh`、`login`、`changePassword`、ApiKey 增删、`clearLogs` **都有限流**。
这三个是漏网的。

**建议**：复用现成的 `recordActionEvent` 分钟级幂等键模式，例如
`notify-test:${minuteStamp()}`、`control:${id}:${minuteStamp()}`——注意**不要**把 action id 放进
action_events 让它无限增长，其实更好的做法是给 `control` 用 `hourlyStamp` 级别的宽松限流。

### P1-4 账号级保活开关改不动（真实功能 bug）

**位置**：`store.ts:346`

```sql
UPDATE accounts SET name=?, remark=?, region_id=?, instance_id=?, site_type=?,
  max_traffic=?, schedule_enabled=?, start_time=?, stop_time=?, shutdown_mode=?
```

**没有 `keep_alive` 列**。而 `saveAccount`（同文件 :326）是有的。后果：
用户在设置页编辑一个已有账号、把「账号级保活」关掉 → 保存成功 → 提示"账号配置已更新" →
**实际没变**。`engine.ts:285` 的 `account.keepAlive !== false` 依旧为 true，保活照常启动。

这是典型的"静默失败"：UI 说成功，行为不变，用户要等到半夜被实例唤醒才发现。

**建议**：把 `keep_alive=?` 加进 UPDATE，并注意 `undefined` 语义（前端传 false 时要真的写 0）。

### P1-5 `scheduled()` 里 `ensureSchema` 没有 try/catch

**位置**：`index.ts:26`

`fetch()` 入口（`index.ts:11-18`）包了 try/catch 但 `scheduled()` 没包。D1 抖动时
`ensureSchema` 抛错 → 整个 cron 轮次抛出 → CF 记为 invocation error，
**本轮监控直接不跑且不会重试**（除非下一轮 CF 再调度）。而在 `fetch` 路径上同样的错误会返回 500
并被前端立刻发现，可观测性差距很大。

**建议**：包 try/catch，失败时 `addLog(warning)` 后 return（下轮自然重试），
而不是让整轮崩掉且不落任何日志。

### P1-6 `jobs` 表每次冷启动先 CREATE 再 DROP

**位置**：`schema.ts:53-70` 建表，`schema.ts:119-120` 迁移里 `DROP TABLE IF EXISTS jobs`

注释说得很清楚"jobs 已废弃、无引用"，但建表语句还留着。结果是每个冷 isolate 都要
`CREATE TABLE jobs ...` + 2 个 `CREATE INDEX` + 然后 `DROP TABLE`。
既多 3 个子请求，也在 D1 里产生无意义的写入计数。

**建议**：直接删掉 `jobs` 相关的 3 条 SCHEMA_STATEMENT（保留 MIGRATIONS 里的 DROP 以兼容已部署库）。

## 五、🟡 P2 清单

### P2-1 断档检查位置错了：每轮白跑 7 个 subrequest
**位置**：`server.ts:1064-1071`

```ts
if (new Date().getUTCMinutes() % 30 === 0) {
  const gapState = triggerState ?? await store.getTriggerState(env);  // 1 次 D1
  await checkTriggerGaps(...);   // 最多 6 次 recordActionEvent
}
```
这段位于**防抖判定之后、槽位抢占之前**。也就是说：每个通过了防抖的轮次都要付 1 次读 +
最多 6 次 `INSERT OR IGNORE`，而其中绝大多数轮次在下一行的 `tryAcquireMonitorSlot` 会被别人抢走
直接 skipped。288 轮/天 × 7 ≈ **2,016 次纯浪费的 D1 操作**。

**建议**：整段挪到 `tryAcquireMonitorSlot` 成功之后、`getConfig` 之前。

### P2-2 日志页 COUNT 每次可能扫 10 万行，撞 D1 读配额
**位置**：`store.ts:424`（`COUNT_CAP = 100000`）

```sql
SELECT COUNT(*) AS c FROM (SELECT 1 FROM logs <where> LIMIT 100000)
```
D1 的 rows-read 按**扫描行数**计。前端日志页支持 10 秒自动刷新（`index.html:3041`），
全天 8,640 次翻页 × 单次低至数千行，很容易逼近 5M 行/天的读阈值。

**建议**：
- COUNT_CAP 降到 2,000（翻到第 40 页时用户已经不需要更多了）；
- 或给 `total` 加 isolate 级短缓存（30 秒）；
- 前端自动刷新在 `document.hidden` 时暂停。

### P2-3 `resolveCronSecret` 每轮都做 AES-GCM 解密
**位置**：`store.ts:115`

即使这一轮最终会被防抖跳过，也要先解密一次。isolate 内 `CDT_MASTER_KEY` 不变，
可以照 `security.ts:34` 的 `keyCache` 写法加一个明文缓存（并带失效标记，避免换密钥后读到旧值）。

### P2-4 `getConfig` 在单个请求里被重复调用
**位置**：`server.ts:341/346`（status 与 widget 都走 `engine.summary` → `getConfig`）、`engine.ts:448/492`

`getConfig` 会 `SELECT key,value FROM settings` **全表**并对每个账号做 2 次 AES 解密。
`runMonitorCycle` 已经为此设计了 `preloadedConfig` 透传，但 `/api/v1/status` 这条路径没有——
前端状态页每次刷新都要重做一遍。

**建议**：给 isolate 内的 config 加 30 秒短缓存，或让 `summary()` 接受已加载的 config。

### P2-5 `api_keys.revoked_at` 是死代码
**位置**：`store.ts:97-106` 建表有这列，`server.ts:95` 有 `if (r.revoked_at) return null`，
但删除是**物理删除**（`store.ts:654`），永远没人写 `revoked_at`。

前端把这个按钮叫「吊销」（`index.html:2870`），后端叫 DELETE。语义上"吊销"应该保留记录以便审计，
现在却把记录一起删了。

**建议**：二选一 —— 要么实现软删除（写 `revoked_at`），要么把 UI 文案改成「删除」并删掉死列。

### P2-6 `withSecurityHeaders` 无条件重建两次 Response
**位置**：`server.ts:686-715`

每次 HTTP 响应都要 `new Response(resp.body, ...)` 再 `new Response(out.body, ...)`。
对 SPA 首页（100 KB+ 的 index.html）是实打实的 CPU 与内存开销，而 Free 计划只有 10 ms。

**建议**：只在确实要 modify header 时才重建，否则原样返回。
