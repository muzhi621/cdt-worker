# CDT Monitor Worker 版 · 审计修复方案（待确认）

> 依据：`docs/audit-2026-09-26.md`（二次审计）
> 性质：**方案文档，未改任何代码**。确认决策点后按 Wave 顺序实施。
> 原则：不改变现有功能语义；每项修复带验证方式；优先修"启用即坏 / 不启用就不安全"的矛盾项。

## 一、先看两个影响方案的事实（本次确认）

| 事实 | 出处 | 对方案的影响 |
| --- | --- | --- |
| 前端每次 API 调用已携带 `X-CDT-CSRF` 头，token 来自登录响应 | `src/web/index.html:1402,1483,1598` | **CSRF 校验只需改后端**，前端零改动，风险极低 |
| 前端「立即监控一次」按钮直接 `fetch("/__cron")`，不带任何密钥 | `src/web/index.html:2284` | 若强制 `CRON_SECRET`，**该按钮也会 401**。方案必须同时兼容：外部触发器（带 key）、前端按钮（带会话）、原生 Cron（内部直调） |

## 二、需你拍板的决策点

### D1（P0）`/__cron` 与定时触发链路怎么修？

| 方案 | 内容 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐）** | **启用原生 Cron Trigger**（`*/5 * * * *`，仅占 5 个免费额度中的 1 个）+ `scheduled()` 内部直调 `runMonitorCycle`（不经 HTTP、天然无鉴权问题）+ `/__cron` 降级为"受保护的手动触发"：**接受管理员会话 或 `CRON_SECRET` 两者之一** | 消除公开 DoS 面；不依赖 GitHub Actions 的延迟；前端按钮经会话继续可用；外部触发器仍可选 | 需改 wrangler.toml + cron.yml + 文档；放弃"省 Cron 额度"的原始顾虑（其实只用 1 个） |
| B | 保持外部触发为主：仅把 `CRON_SECRET` 接线（cron.yml 用 `?key=${{ secrets.CRON_SECRET }}`）+ `/__cron` 额外放行管理员会话（保前端按钮）+ 更新文档 | 改动最小 | 仍依赖 GitHub Actions（高峰延迟数分钟）；外部依赖不断 |
| C | 明确放弃密钥：删除 CRON_SECRET 代码，`/__cron` 保持公开并在文档写明 DoS 权衡 | 零成本 | 审计 P1#1 的 DoS 风险保留 |

> 选 A 时附带动说：`wrangler.toml` 加 `[triggers] crons = ["*/5 * * * *"]`；`DEPLOY-CRON.md` 三处示例补 `?key=`；`cron.yml` 补 secrets。

### D2（P1）CSRF 是否真正校验？

- **推荐：做**。后端加中间件：对"需 admin 的写操作（POST/PUT/DELETE）"比对 `X-CDT-CSRF` 头与 `cdt_csrf` Cookie；**前端已就绪，零前端改动**。未携带/不匹配返回 403。
- 备选：不做，仅在部署文档强制"关闭 workers.dev 路由"（现有文档未强调，风险靠自觉）。

### D3（P2）`init-status` 泄露 `envPasswordSet` 怎么处理？

- **推荐：小改**。`initialized` 保留公开（安装向导路由需要）；`envPasswordSet` 从 init-status **移除**，改为在 `/auth/login` 返回 401 时附带（前端 1613 行同步改一行，登录页仍能提示"可用环境变量恢复密码"）。匿名探测者不再能提前获知是否配置了恢复密码。
- 备选：接受现状（仅泄露一个布尔，攻击者仍需密码），暂不动。

### D4（P2）`[observability] enabled = true` 是否关闭？

- **推荐：保持开启**（排障价值高，正常用量远低于 20 万条/天上限；#1 修复后 `/__cron` 滥用面已收窄）。
- 备选：关闭，省日志额度。

### D5（P3）低危批次做哪些？

建议：**做** #7（Unknown 允许手动启停）、#11（rateMap TTL 清理）、#9（login_attempts 用于 D1 限流）、#8（env 密码登录后前端提示删除 Secret）；**缓做/不做**：#10（AAD 需 `enc:v2` 版本化 + 存量懒迁移，收益低风险中）、#12（`jobs` 表 DROP 需迁移，建议仅标注废弃）、#14（缓存陈旧在文档注明即可）。

## 三、修复项明细（按 Wave 实施）

### Wave 1 — P0/P1（必修，约 1.5~2 小时）

#### 1.1 定时链路重构（对应审计 #1 + #13，选方案 A 时）

| 项 | 改动 |
| --- | --- |
| `wrangler.toml` | 增加 `[triggers]` `crons = ["*/5 * * * *"]` |
| `src/index.ts` | `scheduled()` 改为 `import { runMonitorCycle } from './http/server'` 直接调用（删除模拟 HTTP Request 的绕路，天然绕开密钥问题，同时修掉 #13） |
| `src/http/server.ts` | `/__cron` 校验逻辑改为：`CRON_SECRET` 匹配（`X-Cron-Secret` 头或 `?key=`）**或** 有效管理员会话 → 放行；两者皆无 → 401。`runMonitorCycle` 导出 |
| `.github/workflows/cron.yml` | URL 改 `https://…/__cron?key=${{ secrets.CRON_SECRET }}`，并在仓库 Secrets 配置 `CRON_SECRET`、`WORKER_HOST` |
| `DEPLOY-CRON.md` / `README.md` | 三处示例 URL 补 `?key=`；删除"浏览器直接访问无需登录"的表述，改为"带 key 或登录后访问"；补"原生 Cron 已启用，外部触发为可选备份" |

**验证**：`wrangler dev` 下 ① 无 key 无会话 → 401；② 带 key → 200；③ 登录后前端「立即监控」→ 200；④ 部署后确认 Cron 触发日志出现。

#### 1.2 `/__cron` 防抖原子化（审计 #2）

`store.ts` 新增：
```sql
UPDATE settings SET value = ?, updated_at = datetime('now')
WHERE key = 'last_monitor_run'
  AND (value IS NULL OR CAST(value AS INTEGER) < ?)
```
`runMonitorCycle` 开头调用（参数：`now` 与 `now - (interval*60 - 45)`），`changes === 0` 直接返回 `skipped`；原末尾的 `markMonitorRun` 删除。并发下仅一轮真正执行。

**验证**：并发 5 个同时请求 `/__cron`，日志只出现 1 条"监控周期完成"。

#### 1.3 阿里云签名 `percentEncode` 修正（审计 #4）

`src/provider/aliyun.ts:37-42` 删除 `.replace(/%2B/gi, '%20')` 一行（保留 `~`/`*` 处理）。
**风险**：极低——当前固定签名参数均不含 `+`，线上行为不变；修正的是"参数含 `+` 时的正确性"。
**验证**：新增单测（见 4.1）+ 部署后手动「立即监控一次」确认阿里云 API 正常返回。

### Wave 2 — P2（建议修，约 1 小时）

#### 2.1 CSRF 服务端校验（审计 #3，选 D2=做）

`server.ts`：在鉴权通过后、handler 执行前，对 `method !== 'GET' && route.scope === 'admin'` 的路由校验 `X-CDT-CSRF` 头 === `cdt_csrf` Cookie（常量时间比较）。API Key 调用（Bearer/X-API-Key）不受 CSRF 影响，仅 Session 需要。
**前端**：零改动（已发该头）。
**验证**：登录后改配置 → 200；删掉请求头重放 → 403；API Key 调用 → 不受影响。

#### 2.2 `init-status` 收敛（审计 #6，选 D3=小改）

`server.ts`：init-status 去掉 `envPasswordSet`；`login` 失败响应体加 `envPasswordSet: boolean`；前端 `index.html:1613` 改从登录失败响应读取（1 行）。
**验证**：未登录访问 init-status 不再含该字段；登录页提示行为不变。

#### 2.3 SMTP 冒烟（审计 #5，非代码修复）

新增 `scripts/smoke-smtp.md` 检查单 + 在管理台用现有「通知测试」按钮对 SMTP 通道实测一封（QQ/163 任一）。记录结果到文档；仅当失败时再动代码。

#### 2.4 `Unknown` 不再阻止手动启停（审计 #7）

`engine.ts` `transient()` 移除 `StatusUnknown`（保留 Starting/Stopping/Pending）。
**验证**：新加账号（status=Unknown）可直接手动开机。

#### 2.5 `rateMap` TTL 清理（审计 #11）

`allowRate` 内顺带清理 `now - start > windowMs` 的过期条目（每 100 次调用触发一次全量清扫即可）。

## 四、验证计划（全部完成后执行）

### 4.1 新增自动化测试（修复 #4 等的回归保障）

引入 `vitest`（devDependency），补 4 组单测：
1. `percentEncode`：`+`、空格、`*`、`~`、中文；
2. `dueWithin` / `executeScheduledAction` 幂等键：跨午夜（23:00 窗口）、日期归属、2 小时窗口边界；
3. `billingCache` TTL：UTC 字符串解析（东八区不偏移 8 小时）；
4. `constantTimeEqual` / `verifyPassword` 正反例。

`package.json` 增加 `"test": "vitest run"`；`npm run build` 保持 `tsc --noEmit`。
